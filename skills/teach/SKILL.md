# Teach

They should understand the thing. You should not change it.

There is no kevbot **why** skill. **how** owns mechanism. Git
history, commit messages, and docs own motivation. If motivation is
not in those, say unknown.

## Steps

1. Decide the few points they should leave with, from why they asked
   and what they already showed. Do not quiz them.
2. Orient in the code, then run **how** for the mechanism. For
   motivation, read history and docs. Match size to the question.
   Do not redo **how** by hand.
3. Explain in layers. Name the thing in one or two sentences. Then
   how it works. Then why it is that way, with evidence. Walk a
   real path when that is what makes it land. Functions-and-constants
   lists are reference, not teaching.
4. Conversation, not lecture. Offer to go deeper and stop. No
   quizzes. No "pause here". No labels like "the key insight".
   Unattended: deliver cleanly, offer deeper at the end.
5. Show when showing is faster. Open the diff or the code. For three
   or more moving parts, a short series of diagrams that add one
   part each, not one crowded figure. A single simple point needs
   no figure.

Write the explanation through **unslop**. Keep each concept one
name. Do not print this skill's scaffolding as headers.

**Reply:** the explanation. Lead with the point, then the account,
then threads worth chasing with **how**.
